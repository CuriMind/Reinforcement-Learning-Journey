> **本章回答的问题**：同一个能力（比如"格式别写错"），应该让模型学会，还是让代码来保证？这条分界线该划在哪？为什么"把不可恢复变可恢复"比"训得更准"更划算？

> **证据强度**：📓 争议 / 工程经验 —— 这是全课程第二个性状为"经验"的章。它几乎没有受控实证：没有人做过"同一任务，内化 vs 外化"的大规模 A/B；本章的判断来自工程实践与成本结构，**不是定理**。

> **本章边界**：本章只讲**分工判据**：什么该内化、什么该外化、外化的三种形态、可恢复性设计。**不写**训练框架细节（→第 31 章）；**不写**稳定性与熵管理（→第 25 章）；**不写**环境构造（→第 18 章）。

### 19.1 同一个能力，两个实现位置

> **本节回答的问题**：什么叫"内化"，什么叫"外化"？

**内化（internalize）**：能力写在**策略权重**里，表现为 token 生成的一部分。

**外化（externalize）**：能力写在**harness 代码**里，表现为对生成结果的约束、校验、修复或重试。

**同一个需求的两种实现**，举例说明差别：

| 需求 | 内化做法 | 外化做法 |
|---|---|---|
| JSON 格式正确 | RL 让模型学会输出合法 JSON | 解析失败就重试 / 用 grammar 约束解码 |
| 参数类型正确 | 教模型记住 schema | 调用前用 JSON Schema 校验，错了返回错误信息 |
| 不重复调用同一工具 | 教模型记住已调用 | harness 缓存结果，重复调用直接返回缓存 |
| 上下文不超长 | 教模型"注意长度" | harness 自动摘要/裁剪 |
| 遇到错误要重试 | 教模型学会重试策略 | harness 在失败时按固定策略重试 |

**关键观察**：**外化几乎总是更便宜、更可靠**；但外化不能提升"能力上限"——它只能保证"下限"。

**小结**：内化与外化不是对立的技术路线，而是同一个需求的两个落点：一个提升上限（但可能不稳），一个保证下限（但不长能力）。下一节给判据。

---

### 19.2 判据：四条问题决定归属

> **本节回答的问题**：拿到一个需求，怎么判断该放哪边？

问四个问题，**任一条命中就该外化**：

| # | 判据 | 若命中 | 理由 |
|:--:|---|---|---|
| 1 | **可判定性**：能否用确定性代码可靠实现？ | 外化 | 代码 100% 正确，模型不是 |
| 2 | **零容错性**：错一次的代价是否不可接受？ | 外化 | 训练只能降低概率，不能保证 |
| 3 | **无训练信号**：这个能力是否拿不到奖励/反馈？ | 外化 | 学不到的东西不该指望学会 |
| 4 | **成本不对称**：代码成本远低于训练成本？ | 外化 | 性价比 |

**反向判据**（该内化）：**需要泛化到代码写不出的情形**、**依赖语义理解**、**需要在推理中动态决策**。

**八个常见能力的归属**（这张表可以直接抄）：

| 能力 | 归属 | 理由 |
|---|---|---|
| 输出合法 JSON | **外化**（grammar/重试） | 可判定、零容错 |
| 工具参数符合 schema | **外化**（校验） | 可判定 |
| 选择哪个工具 | **内化** | 依赖语义 |
| 何时放弃 | **内化 + 外化兜底** | 语义判断 + 步数上限 |
| 记住前面调过什么 | **外化**（缓存/状态） | 可判定、无信号 |
| 长文档摘要 | **内化** | 无法用规则 |
| 重试策略 | **外化**（固定退避） | 可判定、无信号 |
| 错误归因（哪步错了） | **外化**（日志）+ 内化（解释） | 记录是代码事，解释是模型事 |

> **工程提示**：把这张表贴在你的设计文档里，逐条标注"我们选了哪边、为什么"。**大量 agentic 系统的失败源于"把可判定的东西交给模型学"**——那是在用训练成本换一个本可免费获得的确定性。

**小结**：四条判据（可判定、零容错、无信号、成本不对称）几乎能覆盖所有决策。最重要的一条是**可判定性**：能用代码保证的，永远不要指望模型学会。

### 19.3 外化的三种形态

> **本节回答的问题**：外化不只是"加个校验"，它有三种介入时机。

| 形态 | 介入时机 | 例子 | 风险 |
|---|---|---|---|
| **前置约束** | 生成**之前**限制动作空间 | grammar 约束解码、工具白名单、只允许特定格式 | 过度约束会压制探索 |
| **后置校验** | 生成**之后**检查 | schema 校验、单元测试、答案比对 | 校验失败要有兜底路径 |
| **过程中介入** | 生成**中间**修正 | 参数错误返回给模型看、缓存重复调用、上下文裁剪 | 介入本身要产生可被模型读到的信号 |

**"过程中介入"最容易被忽略，也最有价值**：因为它同时做了两件事——保证了下限，**并且把错误信息变成了模型可学的信号**。

$$
\text{观测}_s=\text{tool}(a_s),\qquad \text{若失败：}\ \text{观测}_s\leftarrow\text{错误信息}+\text{修复建议}
$$

**逐项读**：① 正常返回工具结果；② 失败时返回**结构化的错误**（而不是空或异常终止）；③ 这个错误信息会进入上下文，成为下一步决策的输入——**于是"外化"间接产生了"内化"的训练信号**。

**外化能带来的收益上界**可以写成一个比较：

$$
\Delta_{\text{externalize}}\le\underbrace{1-P_{\text{policy}}}_{\text{能救回的比例}}\times\underbrace{P_{\text{rescue}}}_{\text{救回的成功率}}\times\underbrace{C_{\text{fail}}}_{\text{单次失败的代价}}
$$

**逐项读**：① 外化只能作用在"模型会失败"的那部分；② 且只能救回其中能被代码救的比例；③ 乘上"失败代价"才是它的真实价值。**这条式子解释了为什么"模型很强时，外化的收益很小"——第一项已经接近 0。**
这是本章最重要的一个洞察：**外化不只是兜底，它还是"内化"的教师**。

**小结**：外化有三种形态，其中"过程中介入"能同时保证下限与产生训练信号。设计 harness 时应该优先考虑这一种。

### 19.4 内化的代价：为什么"学会了"不等于"可靠"

> **本节回答的问题**：如果模型已经学会了，还需要外化吗？

需要，因为内化有三个不可消除的缺陷：

| 缺陷 | 机制 | 后果 |
|---|---|---|
| **概率性** | 模型输出是采样，即使 $p=0.99$ 也有 1% 失败 | 长任务上失败率被放大（$0.99^{50}\approx0.6$） |
| **分布外失效** | 训练没见过的输入 → 行为不可预测 | 真实部署的输入分布与训练不同 |
| **不可审计** | 权重里没有"为什么" | 出问题时无法定位、无法保证 |

**第一条可以量化**（这是最该记住的）：

$$
P(\text{整条轨迹全部正确})\approx p^{S}
$$

**逐项读**：① $p$ 是单步正确率；② $S$ 是步数；③ 即使 $p=0.99$，20 步后只剩 $\approx0.82$。**这意味着"高准确率"在多步任务上会系统性崩塌**——不是模型变差了，是概率在乘法。

> ⚠️ **常见错误**：用单步准确率评估 agent。单步 99% 在多步任务里可能只有 60% 成功率。**必须用端到端成功率**（第 20 章），并把它与 $p^S$ 对比来定位"是单步不行还是步数太多"。

**小结**：内化的三个缺陷（概率性、分布外、不可审计）都无法通过"训得更好"消除。这就是外化永远有位置的根据。

### 19.5 组合：护栏 + 学习

> **本节回答的问题**：既然两者都需要，怎么组合？

**标准架构**：

$$
P(\text{success})=\underbrace{P_{\text{policy}}}_{\text{内化：能力上限}}+\underbrace{\left(1-P_{\text{policy}}\right)\cdot P_{\text{rescue}}}_{\text{外化：失败兜底}}
$$

**逐项读**：① 模型自己搞定的概率；② 失败后由 harness 救回来的概率；③ 两者互补——**外化把"模型失败"从"任务失败"降级为"多花一步"**。

这个分解式给了一个可操作的诊断：

| 观测 | 诊断 | 动作 |
|---|---|---|
| $P_{\text{policy}}$ 低、$P_{\text{rescue}}$ 高 | 模型不行，靠护栏硬撑 | 训练；否则成本高但能跑 |
| $P_{\text{policy}}$ 高、$P_{\text{rescue}}$ 低 | 模型强但没有兜底 | **加护栏**（最划算） |
| 两者都低 | 任务或环境有问题 | 回第 18 章 |
| 两者都高 | 健康 | 优化成本 |

**"护栏 + 学习"的具体形态**：让 harness 先兜底（保证能跑），再把兜底时产生的错误信息回灌训练（提升模型）。这样外化的投入会随时间转化为内化的能力——**而不是永久的技术债**。

**小结**：组合公式把"内化 vs 外化"从二选一变成可测的分解。诊断结论通常是：先加护栏（便宜），再用护栏产生的信号训模型（长期）。

### 19.6 可恢复性：把不可恢复变可恢复

> **本节回答的问题**：为什么说"可恢复"比"更准"更值钱？

Agentic 任务的核心风险不是"错"，而是"**错了不能撤销**"（第 16 章已提过不可逆性）。可恢复性设计把这个问题降级：

| 手段 | 做法 | 把什么变可恢复 |
|---|---|---|
| **沙箱/预演** | 先在隔离环境执行，确认后再落真实系统 | 破坏性副作用 |
| **事务/回滚** | 操作可撤销（快照、版本、撤销日志） | 文件与数据库写入 |
| **幂等** | 同一操作重复执行结果相同 | 重试的安全性 |
| **断点续跑** | 记录状态，失败从断点继续 | 长任务的中断 |
| **人工确认闸门** | 高风险动作前停一下 | 不可逆的决策 |

**为什么它比"训得更准"划算**：训练降低的是失败**概率**，可恢复性降低的是失败的**代价**。当失败不可避免（19.4 的概率论）时，**降低代价的收益是确定的，降低概率的收益是渐近的**。

**可恢复性把期望成本改写**：设不可恢复时单次失败代价为 $C$，可恢复时为 $c$（$c\ll C$，因为只是多花一步），则

$$
\mathbb E[\text{cost}]=\left(1-P\right)\cdot C\ \ \xrightarrow{\ \text{加可恢复性}\ }\ \ P\cdot c_{\text{step}}+(1-P)\cdot c
$$

**逐项读**：① 左边是"失败就报废"的期望成本；② 右边是"失败也能回滚"的版本；③ 由于 $c\ll C$，即使 $P$ 不变，期望成本也下降一个量级——**这正是"降代价"比"降概率"更确定的原因**。
> **工程提示**：列出你的 agent 能做的所有"不可逆操作"（写文件、发请求、扣款、删除）。**每一行都必须有一个可恢复方案**，否则它就是一个"等着被 RL 意外触发"的事故点。

**小结**：可恢复性是 agentic 系统的安全底座。它不提升能力，但把"失败"从灾难降级为成本——在概率无法归零的前提下，这是唯一确定有效的投资。

### 19.7 与第 31 章的接口

> **本节回答的问题**：边界划好之后，工程上怎么落地？

本章给的是**判据**，落地需要三样东西：可插拔的 harness 架构（校验/重试/缓存作为独立中间件）、可观测的失败日志（支撑 19.5 的回灌）、以及训练与部署共用的一套工具定义（否则内化与测试的不是同一个东西）。这三样都在第 31 章。

**回填你的账本表**（第 0 章 0.2 节 · L4/L5 行"标准修法"列）：

```
L4: 过程塑形 ✓（17 章）+ harness 兜底 ✓（本章）
L5: 重复评估 + 置信区间（20 章）、环境与数据（23 章）
    → 待补：稳定性诊断（25 章）、安全约束（26 章）
```
