> **本章回答的问题**：学完之后交什么东西，才算"真的会了"？为什么验收标准要写成"能跑通什么样的对照实验"，而不是"指标达到多少"？

> **证据强度**：📗 教学设计（非研究结论）—— 本章的三级验收与四件套挂钩，依据是第 32 章那套标准做法；**具体分数与阈值需按你的算力与任务调整**（📓）。

> **本章边界**：本章只写**项目设计与验收**：三个项目的目标、最小/完整/加分、验收判据、交付物模板、评分细则、常见失败。**不写**任何新算法；**不写**框架教程（→第 31 章）。

**判据的形式化**：一个合格的验收条件必须写成可判定的布尔式：

$$
\text{pass}=\mathbb 1\left[\text{reproducible}\right]\wedge\mathbb 1\left[\text{has control}\right]\wedge\mathbb 1\left[\text{CI reported}\right]
$$

**逐项读**：① 三项都是布尔量（不是程度）；② 取"与"，任一为假则整体不通过；③ 这就是"结构性判据"的含义——它不关心数值多高，只关心**论证结构是否完整**。

**小结**：验收标准的正确形式是"结构性判据 + 对照 + 复现"，绝对指标只作参考。下一节开始给三个具体项目。

---

### 33.1 设计原则：让"会了"可判定

> **本节回答的问题**：为什么验收标准不能写成"FID 达到 X"或"准确率达到 Y"？

三条原则，按重要性排序：

| 原则 | 要求 | 反例（不要这样写） |
|---|---|---|
| **可判定** | 判据是"通过/不通过"，不是"看起来不错" | "训练收敛良好" |
| **有对照** | 必须有 base 或消融对照（第 15 章的 C1–C4） | "我们提升了 3%" |
| **可复现** | 换机器重跑，结果在预注册容差内 | "我这台机器上是好的" |

**为什么不用绝对指标**：指标的高低依赖模型、数据、算力，**换个设定就不可比**。而"有没有做对照实验"是一个**结构性质**——它不随设定变化。

> **一句话**：这门课验收的不是"你调出了多高的分"，而是"**你能不能证明这个分是真的**"。

**小结**：验收标准的正确形式是"结构性判据 + 对照实验 + 复现条件"。绝对指标只作为参考信息出现，不作为通过条件。

> **工程提示**：项目一最容易走偏成"调参到 500 分"。验收看的不是分数，而是**你能不能诊断出 4 个静默 bug**——分数只是"实现没写错"的入场券。

**小结**：项目一训练的是"从曲线反推实现错误"的能力，这比会调库更接近工程现实。

### 33.2 项目一：从零 PPO + 静默 bug 猎捕

> **本节回答的问题**：不借助任何 RL 库，写出 PPO 并诊断它的错误版本。

**目标**：验证你真正理解了第 6、7 章——不是"调包跑通"，而是"能手写并诊断"。

| 级别 | 要求 | 判据 |
|---|---|---|
| **最小** | 手写 PPO（无 RL 库），CartPole 上稳定解出 | 3 个种子，最终回报均 > 475 |
| **完整** | 完成实验 E1 的四件套（4 个"能跑但错"的版本）并写出诊断 | 4 个版本的判断有 ≥3 个正确，且推理链可复核 |
| **加分** | 在 LunarLander 上复现同样的诊断（环境更敏感） | 至少 2 个 bug 在 LunarLander 上更早暴露，并说明为什么 |

**必交产物**：

```text
e1_ppo/
├── ppo.py            # 手写实现，含 BUG 开关
├── runs/             # 3 种子 × 5 变体的 jsonl
├── curves.png        # return / entropy / clip_frac 三张图
└── diagnose.md       # 填好的诊断表（第 32 章模板）
```

**常见失败**：

| 失败 | 原因 | 判断方法 |
|---|---|---|
| 直接用 RL 库 | 跳过了"手写"这个学习目标 | 代码里有 `import stable_baselines3` |
| 只跑 1 个种子 | 无法区分 b1 与 baseline | 无方差信息 |
| 靠读代码判断 bug | 没有形成"从曲线反推"的能力 | 诊断表里的"依据"栏写的是"我看到了代码" |

> **工程提示**：把"验证器三档（严格/前缀/泄题）"当成项目的一部分交付，而不是调试脚本。**能复现 hack 的人，才有资格谈修复。**

**小结**：项目二把奖励来源、组内优势、缺陷修正、验证器攻击面串成一条链，并强制留出"否定性结果"的位置。

### 33.3 项目二：GRPO + DAPO 补丁 + 解析器 hack 探针

> **本节回答的问题**：在真实 LLM 上跑通 RLVR，并亲手看到一次 hack。

**目标**：验证第 11、12、13 章的连接——从奖励来源到组内优势，再到缺陷修正与验证器攻击面。

| 级别 | 要求 | 判据 |
|---|---|---|
| **最小** | GRPO 跑通一个可验证任务（合成算术即可），监控面板上线 | 六条线（第 25 章）齐备；熵不崩 |
| **完整** | 加 DAPO 补丁（至少 Clip-Higher + 动态采样），并做实验 E3 | 补丁前后熵曲线与 pass@k 有可解释差异；E3 复现 ≥2 种 hack |
| **加分** | 做"同 token 预算"对照（第 15 章 C2） | 给出"RL 的增益是否来自长度"的结论（两种结果都算成功） |

**必交产物**：

```text
e2_grpo/
├── grpo.py / config.yaml
├── verifier.py                # 严格版 + 前缀版 + 泄题版（E3 三档）
├── panel.png                  # 六条监控线
├── hack_samples.md            # ≥5 条"验证器判对、人类判错"
└── report.md                  # 对照表 + 结论
```

**验收的关键点**：**报告里必须有"否定性结果"的空间**。如果 C2 对照显示增益消失，正确的交付是"增益来自长度"，而不是"实验失败"。

**常见失败**：

| 失败 | 原因 | 判断方法 |
|---|---|---|
| 只报 pass@1 | 无法排除长度补偿 | 缺 C2 对照 |
| 验证器写成前缀匹配却不知道 | 自己造了 hack 入口 | E3 无法复现 hack（因为一直在被 hack） |
| 补丁全开 | 无法归因（第 13 章纪律） | 一次改了两个以上变量 |

**预算对等的判据**：

$$
\sum_{\text{seq}}\text{tokens}\ \approx\ \sum_{\text{step}}\text{tokens}\quad(\pm 10\%)
$$

**逐项读**：① 两组的 token 总消耗必须可比；② 允许 ±10% 的实现差异；③ 若步骤级需要更多预算才"更好"，那结论是"它更贵"，不是"它更强"。

**小结**：项目三的难点不在实现，而在**把对照做公平**。预算不对等是这个项目最常见的假实验来源。

### 33.4 项目三：多轮工具的步骤级信用分配

> **本节回答的问题**：在 agentic 场景里，把序列级优势换成步骤级，差别在哪？

**目标**：验证第 16、17、18 章的连接——形式化粒度、信用分配、环境信号。

| 级别 | 要求 | 判据 |
|---|---|---|
| **最小** | 双工具环境（查表 + 计算）跑通 GRPO | 成功率 > 0 且优于随机；步数分布可报 |
| **完整** | 实现步骤级优势（第 17 章通用形式），与序列级做对照（E4） | 两组成功率带 95% CI；给出"偏差↓方差↑"的证据 |
| **加分** | 加"隐藏测试集 + 噪声工具"两个变体 | 证明"反作弊靠环境侧约束"（第 18 章） |

**必交产物**：

```text
e4_agent_credit/
├── env.py                  # 三变体：open / hidden / noisy
├── credit.py               # seq / step 两种优势
├── advantage_dist.png      # 步骤级优势分布
└── report.md               # 6 组结果表 + 决策段落
```

**关键判据（这一项最容易做成假实验）**：两组必须**固定总 token 预算**再比较。若不固定，"步骤级更好"可能只是"它花了更多采样"。

**常见失败**：

| 失败 | 原因 | 判断方法 |
|---|---|---|
| 预算不对等 | 步骤级需要更多 rollout 才有统计量 | 两组 tokens 不一致 |
| 中间奖励自己编的 | 注入了先验却未声明 | 报告里没有"无中间奖励"的消融 |
| 隐藏测试集不隐藏 | 评估实例出现在训练 rollout 里 | 无独立 seed 区间 |

### 33.5 三级验收表（可直接作为评分表）

> **本节回答的问题**：怎么给分？

| 维度 | 权重 | 最小级（60 分） | 完整级（85 分） | 加分（100 分） |
|---|:--:|---|---|---|
| **能跑通** | 30% | 3 种子可复现 | 同左 | 换机器仍在容差内 |
| **有对照** | 30% | 有 base 对照 | 有随机/恒 0 对照 | 有同预算对照 |
| **有诊断** | 20% | 六条监控线 | 四件套冒烟测试 | 定位到一个非预期现象 |
| **有诚实结论** | 10% | 报告指标含 CI | 报告否定性结果 | 主动指出自己结论的边界 |
| **可复现** | 10% | 种子+版本清单 | 预注册容差 | 他人按 README 能复现 |

**评分公式**（用于自查，不是自动打分）：

$$
\text{score}=30\,p_{\text{run}}+30\,p_{\text{ctrl}}+20\,p_{\text{diag}}+10\,p_{\text{honest}}+10\,p_{\text{repro}}
$$

**逐项读**：① $p$ 是各维度的达成比例（0–1）；② "有诚实结论"这一项（10 分）是**用来奖励否定性结果的**——如果 C2 对照表明增益消失，报告这个结论应当**拿满分而不是零分**；③ 总分不是目的，五个维度缺一项都说明某个学习目标没达到。

> ⚠️ **常见错误**：为了拿"完整级"而堆实验，却没有一项做透。**验收看的是"每个维度都达标"，不是"实验数量多"**。

**小结**：评分表的价值在结构，不在分数。五个维度分别对应五个学习目标：能跑、会对照、会诊断、敢说否定、可复现。

**容差的事前定义**：

$$
\epsilon_{\text{tol}}=s_{\text{seed}},\qquad \text{复现通过}\iff\left|\text{run}_1-\text{run}_2\right|\le\epsilon_{\text{tol}}
$$

**逐项读**：① 容差取"种子间标准差"这一档；② 超过它说明这次跑出了离群点；③ 关键是它在跑实验**之前**就定好。

**小结**：交付物模板的六节分别对应可复现、主结果、对照、诊断、诚实结论、清单。少一节就会在某类质疑前失守。

### 33.6 交付物模板

> **本节回答的问题**：报告怎么组织？

```markdown
# <项目名> 结题报告

## 1. 设置（可复现性）
- 代码 commit、依赖锁、模型 revision、硬件
- 三类种子；预注册容差

## 2. 主结果
| 配置 | 3 种子结果 | 均值 ± 极差 | 95% CI |
（每个数字都必须有 CI 或极差）

## 3. 对照实验
- C1 reward 恒 0：策略是否变化（附曲线）
- C2 reward 随机：是否学到东西
- C3 单 batch：能否过拟合
- C4 黄金轨迹：是否得满分
- 同 token 预算对照（项目二/三必做）

## 4. 诊断
- 六条监控线（图）
- 一次真实的故障与定位过程（这是加分项）

## 5. 诚实结论
- 支持了什么
- **否定了什么**（这一节不许为空）
- 结论的边界（在什么条件下不成立）

## 6. 复现清单
（第 32.7 节的十项打勾）
```

**第 5 节的"否定了什么"不允许为空**——这是本课程的设计要求：**任何一次认真的实验都会否定某个预期**。写不出否定，通常说明实验设计不够严格（或没有对照）。

三个项目覆盖的能力可以写成一个覆盖度：

$$
\text{coverage}=\frac{\left|\{\text{算法},\ \text{奖励},\ \text{粒度}\}\ \text{中已动手的}\right|}{3}
$$

**逐项读**：① 三个维度各自对应一个项目；② coverage=3 才算"主干完整"；③ 只做其中一个也能拿分，但那说明你的经验是单点的。

**小结**：三个项目对应"算法 → 奖励 → 粒度"三段主干，而共同的验收方式（对照/诊断/复现）才是课程真正想留下的东西。

### 33.7 三个项目合起来教了什么

> **本节回答的问题**：为什么是这三个，而不是别的？

| 项目 | 对应的能力 | 对应章节 |
|---|---|---|
| 一 | **算法实现 + 静默 bug 诊断** | 6、7、32 |
| 二 | **奖励设计 + 验证器工程 + 缺陷修正** | 11、12、13 |
| 三 | **形式化粒度 + 信用分配 + 环境信号** | 16、17、18 |

三个项目串起来就是全课程的主干：**算法 → 奖励 → 粒度**。而它们共同的验收方式（对照 + 诊断 + 复现）才是这门课真正想留下的东西——**因为具体算法会过时，而"如何证明一个说法是真的"不会**。

**回填你的账本表**（第 0 章 0.2 节 · 最终复盘，第 0 章 0.6 节）：

```
L1–L5 五行：请填上你实际跑出的读数（成功率、方差、成本）
若某行为空 → 那一级的粒度你没有真正动手过
```

**本章收束**：① 本章给了三个项目（PPO 手写与 bug 猎捕、GRPO 与验证器 hack、多轮步骤级信用分配）与一套"可判定 + 有对照 + 可复现"的三级验收表，并明确规定"否定性结果必须占一席"；② 与全书的接口是：回到第 0 章的粒度账本表做复盘——**能填满五行，才算学完**；③ 留下的未解问题不是技术性的，而是教学性的（📓 如何评估"判断力"而非"分数"），它正是本课程设计时最不确定的一点。
